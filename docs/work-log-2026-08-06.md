# 作業記録 — 2026-08-06

## 本日の到達点

DeskNet'sの認証済みEdgeをLocal Workerから操作し、参加者と設備の空きを確認して、ユーザーの明示的な最終承認後にだけ予定を登録するPoCを拡張した。

現在の会話フローは次のとおり。

1. 参加者と期間を指定して共通の空き時間を検索する。
2. 指定設備の空きと参加者全員の空きをAND条件で絞る。
3. 時刻順に表示された候補カードをクリックする。
4. 日時、参加者、会議室をまとめて確認する。
5. 本人を含む出席者へのメール送信有無を選択する。
6. DeskNet'sの未保存フォームを準備し、`awaiting_approval`で停止する。
7. Web Consoleの最終確認ボタンを押した場合だけDeskNet'sの「追加」を実行する。

## 実装した内容

### Intent解析

- 日本語の次の表現を決定的パーサーで処理できるようにした。
  - `今日`
  - `明日`
  - `1週間以内`（今日を含む7日間）
  - `今月中`（今日から月末まで）
- 最大検索期間を31日に制限した。
- Azure OpenAI Structured Outputsを利用するIntent Analyzerを追加した。
- LLM出力をJSON Schemaで次の構造に限定した。
  - intent
  - participantNames
  - dateStart / dateEnd
  - durationMinutes
  - facilityQuery
  - candidateNumber
  - sendEmail
  - title
- LLMはIntent抽出だけを担当し、過去除外、期間制限、会話状態、書込みPolicy、最終承認はコード側で再検証する。
- Azure OpenAIが未設定または利用不能な場合は、決定的パーサーへフォールバックする。
- Web Consoleに現在の解析元を表示する。
  - `Azure OpenAI`
  - `決定的フォールバック`

現在のローカル環境では以下が未設定のため、実行時は決定的フォールバックになっている。

```text
AZURE_OPENAI_ENDPOINT
AZURE_OPENAI_API_KEY
AZURE_OPENAI_DEPLOYMENT
```

秘密情報はリポジトリやプロンプトへ保存しないこと。

### 日時と候補の安全性

- 過去期間はブラウザ操作前に拒否する。
- 当日は開始時刻を過ぎた候補を除外する。
- 候補表示、候補選択、メール選択、最終承認の各時点で開始時刻を再検証する。
- 08:00〜18:00を30分刻みで探索し、1時間候補を生成する。
- 複数日検索では参加者の選択を維持したまま日付を切り替え、日ごとに参加者と全社設備のbusy intervalを抽出する。
- 設備指定後は、参加者全員と指定設備がともに空いている候補だけを返す。
- 設備候補は時間昇順で最大50件をクリック可能に表示する。

### 予約と最終承認

- 番号選択または候補カードのクリックは候補選択だけを行い、登録しない。
- メール送信の`はい／いいえ`を別状態で保持する。
- 選択した日時、参加者、設備、メール状態をDeskNet'sフォームへ入力する。
- 会話上の予約指示だけではDeskNet'sの最終「追加」を押さない。
- Web Consoleの独立した最終確認ボタンから`approve` APIを呼んだ場合だけ、最終登録を再開する。
- Policyは最終操作にwriteモードと明示承認済みの両方を要求する。
- 登録後は予定を開き直し、件名、日時、参加者、設備を確認する。
- 登録後の検証が不完全でも、自動再試行しない。

### Web Console UX

- 初回の参加者空き時間回答では設備カードを表示しない。
- 設備を質問した後だけ、`参加者全員 × 指定設備`の候補カードを表示する。
- 候補クリック後に次をまとめて表示する。
  - 日時
  - 参加者

- メールあり／なしのボタンを追加した。

### 実行安定性

- 専用Edgeを複数Runが同時操作しないよう、DeskNet's RunをAPI側で直列キューにした。
- ユーザー操作と検証E2Eが同時実行され、ダイアログ操作が衝突した問題を解消した。
- DeskNet'sのスクリーンショットが停止しても、読取り処理全体を失敗させないようにした。
  - 3秒でキャプチャを打ち切る。
  - プレースホルダー証跡を保存する。
  - Observation summaryにタイムアウトを明記する。
- 成否後の未保存フォーム破棄を確認した。`awaiting_approval`中だけは最終承認のためフォームを保持する。

## Remote化の結論

現状のWorkerは`127.0.0.1:9222`の認証済みEdgeを操作するため、そのままRemoteサーバーへ移すことはできない。

推奨構成：

```text
Remote Web / API
       │ HTTPSまたはWebSocket（Local Workerから外向き接続）
       ▼
ユーザーPCのLocal Worker
       │ loopback CDP
       ▼
認証済みEdge → DeskNet's
```

- 会話、ジョブ管理、監査はRemoteに置く。
- Edge操作とDeskNet's認証状態はLocal Workerに残す。
- RemoteからユーザーPCへの受信ポートは開けない。
- Cookie、パスワード、EdgeプロファイルはPC外へ出さない。
- 最終確定はLocal側にも明示表示する。

## Local Worker配布案

### PoC

1. コード署名済みのZIPまたはSetup.exeをTeamsの限定チャネルで配布する。
2. ユーザーが解凍してSetup.exeを実行する。
3. Entra IDでサインインする。
4. 情報システムが別経路で発行したワンタイム登録コードを入力する。
5. Local Workerが端末固有鍵を生成し、Remoteへ登録する。

共通の長期パスキーは使用しない。登録コードはユーザーまたは端末に紐付け、1回限り・短時間で失効させる。登録後の認証情報はWindows Credential ManagerまたはDPAPIへ保存し、Remote側から端末登録を失効できるようにする。

### 本番

- 署名済みMSIX/MSIをIntuneまたはCompany Portalで配布する。
- Teamsアプリは会話画面、状態確認、インストーラー案内を担当する。
- TeamsアプリパッケージだけではWindowsのLocal Workerを自動インストールできない。
- Publisher署名または特定ハッシュだけを情報システムの許可対象にする。
